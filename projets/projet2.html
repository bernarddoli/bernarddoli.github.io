Synchronisation des données avec Lsyncd

Linux Lsyncd / Rsync SSH Administration système

Mise en œuvre d'une solution de réplication automatique de fichiers en temps réel entre serveurs Linux, s'appuyant sur Lsyncd, rsync et un tunnel SSH sans mot de passe. Le tout conçu pour garantir la cohérence des données, la continuité de service et la sécurité des transferts, modification après modification.

Introduction

Ce projet met en œuvre une solution de synchronisation de fichiers en temps réel entre deux serveurs Linux. Elle repose sur Lsyncd (Live Syncing Daemon), un démon qui surveille en continu les modifications du système de fichiers via inotify et déclenche automatiquement une synchronisation par rsync à travers un tunnel SSH sécurisé.

L'objectif est de maintenir en permanence une copie cohérente et à jour d'un ou plusieurs répertoires sur un serveur distant, sans intervention manuelle.

Contexte & Objectifs

Dans le cadre de ma formation en administration système, j'ai souhaité expérimenter des mécanismes de haute disponibilité des données sur Linux. Les objectifs du projet :

  • Comprendre le fonctionnement de la synchronisation en temps réel via inotify
  • Déployer une solution automatisée de mise en miroir avec Lsyncd
  • Garantir la cohérence et l'intégrité des fichiers entre un serveur source et un serveur distant
  • Sécuriser les transferts SSH avec une clé dédiée sans passphrase
  • Explorer des architectures avancées : une source vers plusieurs cibles, plusieurs sources vers une cible

Architecture

Synchronisation mono-directionnelle entre deux serveurs sur le même réseau local. Dès qu'un fichier est créé, modifié ou supprimé dans le répertoire source, Lsyncd le détecte via inotify et déclenche un rsync vers la destination via SSH. 


  Serveur 1 (192.168.100.225)          Serveur 2 (192.168.100.226)
  ┌─────────────────────────┐           ┌─────────────────────────┐
  │  /home/user1/           │           │  /home/user2/           │
  │                         │           │                         │
  │  lsyncd                 │           │                         │
  │  └─ inotify surveille   │──rsync──▶ │  fichiers répliqués     │
  │     les changements     │    SSH    │  en temps réel          │
  │                         │           │                         │
  │  clé: /root/.ssh/id_sync│           │                         │
  └─────────────────────────┘           └─────────────────────────┘

Implémentation technique

1 — Prérequis sur les deux serveurs

Sur les deux machines (Serveur1 et Serveur2), mettre à jour le système et installer rsync ainsi que lsyncd avec les droits root : 

apt update && apt upgrade -y
apt install rsync lsyncd -y

2 — Authentification SSH sans mot de passe

Lsyncd doit pouvoir se connecter au serveur distant sans intervention humaine. On génère une clé SSH dédiée sans passphrase sur le Serveur1 : 

root@SRV1# ssh-keygen -t ed25519 -f /root/.ssh/id_sync -C "lsyncd-sync"
# -t ed25519  : algorithme moderne, clé courte et robuste
# -f          : chemin de la clé générée (privée + publique)
# -C          : commentaire descriptif visible dans authorized_keys

Avant de copier la clé, s'assurer que l'authentification par mot de passe est activée sur Serveur2 (nécessaire uniquement pour cette étape initiale). Éditer /etc/ssh/sshd_config sur Serveur2 : 

PermitRootLogin yes         # autoriser root à se connecter via SSH
PasswordAuthentication yes  # autoriser l'auth par mot de passe (temporaire)

# Redémarrer SSH pour appliquer les changements :
systemctl restart sshd
⚠ Bonne pratique : une fois la clé copiée et testée, repasser PasswordAuthentication no sur Serveur2. Laisser l'authentification par mot de passe active en production expose le serveur aux attaques par force brute.

Depuis Serveur1, copier la clé publique vers Serveur2 :

ssh-copy-id -i /root/.ssh/id_sync.pub root@192.168.100.226

Vérifier la présence de la clé sur Serveur2 : cat /root/.ssh/authorized_keys

Tester la connexion sans mot de passe depuis Serveur1 :

ssh -i /root/.ssh/id_sync root@192.168.100.226 "echo connexion OK"
# Résultat attendu : "connexion OK" sans aucune demande de mot de passe

3 — Créer les répertoires

Sur Serveur1, créer les répertoires sources à surveiller :

mkdir -p /home/user1/demo1
mkdir -p /home/user1/demo2

Sur Serveur2, créer les répertoires de destination :

mkdir -p /home/user2/rep-sync1
mkdir -p /home/user2/rep-sync2

4 — Test manuel de rsync

Avant de configurer Lsyncd, valider que rsync fonctionne correctement entre les deux serveurs : 

# Créer du contenu de test sur Serveur1
echo "HELLO WORLD" > /home/user1/demo1/test.txt

# Synchronisation manuelle vers Serveur2
rsync -avz --delete \
    -e "ssh -i /root/.ssh/id_sync" \
    /home/user1/demo1/ \
    root@192.168.100.226:/home/user2/rep-sync1/

# -a  : mode archive (préserve permissions, timestamps, liens symboliques)
# -v  : verbeux (affiche les fichiers transférés)
# -z  : compression des données pendant le transfert
# --delete : supprime sur la cible les fichiers absents de la source
# -e  : spécifie le tunnel SSH avec la clé dédiée

Le fichier test.txt doit apparaître dans /home/user2/rep-sync1/ sur Serveur2 sans erreur. Si c'est le cas, rsync et SSH sont correctement configurés.

5 — Configuration de Lsyncd

Créer le fichier de configuration et le répertoire de logs :

mkdir -p /etc/lsyncd
mkdir -p /var/log/lsyncd
nano /etc/lsyncd/lsyncd.conf.lua

Copier le contenu suivant. Chaque bloc sync gère une paire source/cible de manière indépendante — c'est la règle fondamentale de Lsyncd : un bloc sync par paire source/cible. 

settings {
    logfile        = "/var/log/lsyncd/lsyncd.log",
    statusFile     = "/var/log/lsyncd/lsyncd.status",
    nodaemon       = false,
    statusInterval = 5,
}

-- Bloc 1 : demo1 → rep-sync1
sync {
    default.rsync,
    source = "/home/user1/demo1/",
    target = "root@192.168.100.226:/home/user2/rep-sync1",
    rsync  = {
        archive  = true,
        compress = true,
        verbose  = true,
        rsh      = "ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no"
    }
}

-- Bloc 2 : demo2 → rep-sync2
sync {
    default.rsync,
    source = "/home/user1/demo2/",
    target = "root@192.168.100.226:/home/user2/rep-sync2",
    rsync  = {
        archive  = true,
        compress = true,
        verbose  = true,
        rsh      = "ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no"
    }
}

6 — Démarrer et activer le service

# Démarrer le service immédiatement
systemctl start lsyncd

# Activer le démarrage automatique au boot
systemctl enable lsyncd

# Vérifier que le service est actif (active running)
systemctl status lsyncd

# Suivre les logs en temps réel pour valider la synchronisation
tail -f /var/log/lsyncd/lsyncd.log

Cas d'usage avancés

Deux sources vers une même destination

Il n'est pas possible de déclarer plusieurs sources dans un seul bloc sync. La solution est d'utiliser deux blocs pointant vers la même target : 

  Serveur1
  /home/user1/demo1/  ──┐
                        ├──▶  Serveur2 : /home/user2/rep-sync1
  /home/user1/demo2/  ──┘
-- Bloc 1 : demo1 → rep-sync1
sync {
    default.rsync,
    source = "/home/user1/demo1/",
    target = "root@192.168.100.226:/home/user2/rep-sync1",
    rsync  = {
        archive  = true,
        compress = true,
        verbose  = true,
        rsh      = "ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no"
    }
}

-- Bloc 2 : demo2 → rep-sync1 (même destination)
sync {
    default.rsync,
    source = "/home/user1/demo2/",
    target = "root@192.168.100.226:/home/user2/rep-sync1",
    rsync  = {
        archive  = true,
        compress = true,
        verbose  = true,
        rsh      = "ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no"
    }
}
⚠ Attention aux conflits de noms : si demo1/ et demo2/ contiennent un fichier portant le même nom, le dernier rsync à s'exécuter écrasera silencieusement le précédent. Lsyncd ne gère pas les conflits. S'assurer que les sources ont des contenus disjoints.

Une source vers plusieurs serveurs distants

Ajouter un bloc sync par serveur cible. Lsyncd exécute chaque bloc dans un processus parallèle et indépendant — si un serveur est hors ligne, les autres continuent de se synchroniser normalement. 

  Serveur1 /home/user1/demo1/
    │
    ├──▶  192.168.100.226  /home/user2/  (Serveur2)
    ├──▶  192.168.100.227  /home/user3/  (Serveur3)
    ├──▶  192.168.100.228  /home/user4/  (Serveur4)
    └──▶  192.168.100.229  /home/user5/  (Serveur5)
settings {
    logfile        = "/var/log/lsyncd/lsyncd.log",
    statusFile     = "/var/log/lsyncd/lsyncd.status",
    nodaemon       = false,
    statusInterval = 5,
}

-- Serveur2
sync {
    default.rsync,
    source = "/home/user1/demo1/",
    target = "root@192.168.100.226:/home/user2",
    rsync  = { archive=true, compress=true, verbose=true,
               rsh="ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no" }
}

-- Serveur3
sync {
    default.rsync,
    source = "/home/user1/demo1/",
    target = "root@192.168.100.227:/home/user3",
    rsync  = { archive=true, compress=true, verbose=true,
               rsh="ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no" }
}

-- Serveur4
sync {
    default.rsync,
    source = "/home/user1/demo1/",
    target = "root@192.168.100.228:/home/user4",
    rsync  = { archive=true, compress=true, verbose=true,
               rsh="ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no" }
}

-- Serveur5
sync {
    default.rsync,
    source = "/home/user1/demo1/",
    target = "root@192.168.100.229:/home/user5",
    rsync  = { archive=true, compress=true, verbose=true,
               rsh="ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no" }
}
⚠ Ne pas oublier : copier la clé SSH sur chaque serveur cible avec ssh-copy-id et tester la connexion depuis Serveur1 avant de démarrer Lsyncd. Un serveur sans la clé bloquera son bloc de synchronisation sans affecter les autres.

Résultats & Tests

Les tests ont été conduits sur un réseau local avec deux machines virtuelles Debian 12.

  • Latence de synchronisation : les modifications sont répliquées en moins d'une seconde pour des fichiers de taille standard (< 10 Mo)
  • Robustesse : en cas d'interruption réseau, Lsyncd reprend la synchronisation automatiquement dès que la connexion est rétablie, sans perte de données
  • Monitoring : les fichiers /var/log/lsyncd/lsyncd.log et lsyncd.status permettent de suivre l'activité en temps réel et de diagnostiquer d'éventuelles erreurs
  • Parallélisme : les deux blocs sync s'exécutent en parallèle sans interférence, même lorsque les deux répertoires sources sont modifiés simultanément
Bilan : la solution est opérationnelle, légère en ressources et adaptée à des environnements de production modestes. Pour des besoins plus avancés — synchronisation bi-directionnelle, gestion de conflits — des outils comme Unison ou GlusterFS seraient à envisager.

Conclusion

Ce projet m'a permis de maîtriser concrètement la mise en place d'une solution de réplication de fichiers en temps réel sur Linux. Au-delà de la configuration technique, il illustre des enjeux importants en administration système : sécurisation des accès SSH, gestion des droits, surveillance via les logs, et conception d'architectures de données résilientes.

Les compétences mobilisées — inotify, rsync, SSH par clé, Lsyncd — sont directement transférables à des contextes professionnels tels que la sauvegarde automatisée, la haute disponibilité ou la mise en miroir de serveurs de fichiers.
