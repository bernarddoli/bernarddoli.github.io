Synchronisation des données

Harmonisation des données systèmes

Une solution de synchronisation fluide adaptées aux défis spécifiques, modification après modification. Cette solution donne aux entreprises les moyens de prospérer : synchronisation fluide des fichiers, détection intelligente des modifications, le tout conçu pour garantir une cohérence durable des données sur le long terme.

Introduction

Cette solution basée sur Lsyncd, conçue pour assurer une mise en miroir fiable des fichiers. Elle intègre une synchronisation en temps réel ainsi qu’une automatisation intelligente, garantissant la cohérence, la sécurité et la sauvegarde ainsi que la réplication automatisées de vos données.

Contexte & Objectifs

Dans le cadre de ma formation, j’ai souhaité mettre en pratique des mécanismes de synchronisation et de disponibilité des données en environnement Linux. Pour cela, j’ai mis en œuvre une solution basée sur Lsyncd (Live Syncing Daemon), permettant d’assurer la réplication automatique de fichiers entre plusieurs systèmes. Les objectifs principaux étaient :

  • Comprendre le fonctionnement de la synchronisation en temps réel
  • Mettre en place une solution automatisée de mise en miroir de données avec Lsyncd
  • Garantir la cohérence et l’intégrité des fichiers entre un serveur source et un serveur distant
  • Renforcer la disponibilité des données dans un contexte de continuité de service
  • Appliquer de bonnes pratiques de sécurisation des transferts (via SSH, permissions, etc.)

Fonctionnement

Lsyncd (Live Syncing Daemon) est un outil de synchronisation de fichiers en temps réel qui repose sur un mécanisme de surveillance du système de fichiers.

  • Lsyncd surveille en continu un répertoire source grâce à inotify (événements système Linux)
  • Lorsqu’un fichier est créé, modifié ou supprimé, un événement est détecté
  • Lsyncd déclenche ensuite une commande de synchronisation (souvent via rsync)
  • Les fichiers sont alors répliqués vers un serveur distant ou un autre répertoire local

Implementation technique

Structure pour une synchronisation mono-directionnelle (Serveur1 vers serveur2)

Prérequis sur les deux serveurs

Sur Serveur1 (192.168.100.225) et Serveur2 (192.168.100.226), nous allons installé lsyncd avec les permissions root

apt update && apt upgrade -y
apt install rsync lsyncd -y
# mise à jour du système et installations

Authentification SSH sans mot de passe

Sur le Serveur source (Server1), généré une clé SSH. Cette clé sera utilise afin d'assurer une synchronisation sécurisée. Nous n'utiliserons pas de passphrase. Le passphrase nécessitera la presence d'un utilisateur pendant l’établissement de la connexion distante avant la synchronisation. 

root@SRV-SYNC01# ssh-keygen -t ed25519 -f /root/.ssh/id_sync -C "lsyncd-sync"
# -t : Spécifie le type d'algorithme cryptographique à utiliser.
# -f : Définit le chemin et nom du fichier de sortie.
# -C : Ajoute un commentaire à la clé publique. Une étiquette descriptive.

A present, nous allons copié la clé publique (de Server1) sur le serveur de destination (Server2)

Mais avant cela, il faut se rassurer que la connexion SSH par mot de passe est activée sur le Serveur 2 et que l'utilisateur root est autorisé à se connecter via SSH. Connectez-vous sur le Server2 et modifié le fichier /etc/ssh/sshd_config, cherche et modifie les lignes PermitRootLogin et PasswordAuthentication. 

nano /etc/ssh/sshd_config
PermitRootLogin yes          # autoriser root à se connecter 
PasswordAuthentication yes   # autoriser l'auth par mot de passe
# Puis redémarre SSH : systemctl restart sshd

Après modification, nous effectuons finalement la copie. sur Server1 nous allons tapez cette commande : 

ssh-copy-id -i /root/.ssh/id_sync.pub root@192.168.100.226

Sur le Server2, nous allons afficher le fichier authorized_keys. en utilisant la commande cat /root/.ssh/authorized_keys.

Test de connectivé entre Server1 vers Server2

Sur Server1 (192.168.100.225), nous allons tenter une connexion ssh vers le Server2 avec l'utilisateur root

ssh -i /root/.ssh/id_sync root@192.168.100.226 "echo connexion OK"

La sortie: connexion OK sans qu'on ne demande un mot de passe confirme que la clé est bien installée.

⚠ Avertissement : autoriser une connexion distante via l'utilisateur peut avoir des consequence dangereux. Pour pallier a cela on peut faire une copie manuel depuis le Serveur 2 dans /root/.ssh.

Repertoires de synchronisation

Sur le Sur Server1, nous allons creer le(s) repertoire(s) source que nous voulions synchroniser sur le server2 au cas où ce(s) repertoire(s) n'existe(nt) pas. Dans notre cas, creons demo1 et demo2 

mkdir -p /home/user1/demo1
mkdir -p /home/user1/demo2

Sur Server2, nous allons cette fois-ci creer le(s) repertoire(s) de destination qui vous recevoir les donnees du server1. (rep-sync1 et rep-sync2) 

mkdir -p /home/user2/rep-sync1
mkdir -p /home/user2/rep-sync2

Test de synchronisation manuel

Avant de configurer lsyncd, nous allons vérifier que rsync fonctionne bien sur les deux servers. Sur Serveur 1, nous allons creer du contenu et tester la synchronisation. 

# Creation de contenu
touch /home/user1/demo1/fichier.txt
touch /home/user1/demo1/fichier.txt
echo "HELLO WORLD" > /home/user1/demo1/fichier.txt
touch "SECRET TEXTE" > /home/user1/demo1/fichier.txt

# synchronisation manuel
rsync -avz --delete \
    -e "ssh -i /root/.ssh/id_sync" \
    /home/user1/demo1/ \
    root@192.168.100.226:/home/user2/rep-sync1/

# -a Mode archive (permissions, timestamps, récursif)
# -v Verbeux (logs)
# -z Compression pendant le transfert
# -e Spécifie le tunnel SSH avec la clé dédiée

Les fichiers doivent se transférer sans erreur. Les repertoires /home/user2/rep-sync1 et /home/user2/rep-sync1 doivent avoir le meme contenu due a synchronisation.

lsyncd sur le server1

Crée le fichier de configuration

mkdir -p /etc/lsyncd
nano /etc/lsyncd/lsyncd.conf.lua
# répertoire de logs
mkdir -p /var/log/lsyncd

Copier le contenu ci-dessus


settings {
    logfile    = "/var/log/lsyncd/lsyncd.log",
    statusFile = "/var/log/lsyncd/lsyncd.status",
    nodaemon   = false,
    statusInterval =  5,
}
# BLOC-2 demo1 vers rep-sync1
sync {
    default.rsync,
    source  = "/home/user1/demo1/",
    target  = "root@192.168.100.226:/home/user2/rep-sync1",
    rsync   = {
        archive  = true,
        compress = true,
        verbose  = true,
        rsh      = "ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no"
    }
}
# BLOC-1 demo2 vers rep-sync2
sync {
    default.rsync,
    source  = "/home/user1/demo2/",
    target  = "root@192.168.100.226:/home/user2/rep-sync2",
    rsync   = {
        archive  = true,
        compress = true,
        verbose  = true,
        rsh      = "ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no"
    }
}

lsyncd fonctionne selon la regle : une source, une target par bloc sync. la configuration est prete pour une synchronisation des deux repertoires en cas d'un evenement detecter dans un des repertoires sources.

Démarrer et activer lsyncd

# Démarrer le service
systemctl start lsyncd
# Activer au démarrage automatique
systemctl enable lsyncd
# Vérifier le statut
systemctl status lsyncd

Résultats & Tests

Les tests ont été effectués sur une machine virtuelle Kali Linux, avec une liste de hashes MD5 générés localement à partir de mots de passe connus.

  • Mots de passe simples (< 6 car.) : retrouvés en moins de 2 secondes
  • Mots du dictionnaire : 95 % retrouvés en moins d'une minute
  • Avec mutations : +12 % de taux de succès supplémentaire
  • Mots complexes (> 10 car. mixtes) : non retrouvés (temps prohibitif sans GPU)
Conclusion des tests : Un mot de passe d'au moins 12 caractères combinant majuscules, minuscules, chiffres et symboles résiste efficacement à toutes les attaques testées. L'usage d'un gestionnaire comme KeePass est fortement recommandé.

Limites & Éthique

Deux sources vers une destionation

  Serveur 1                        
/home/user1/demo1/  ─────┐            Server2
                         ├────► /home/user2/rep-sync1
/home/user1/demo2/  ─────┘

Deux sources (/home/user1/demo1/", "/home/user1/demo2/") vers une seule destination (/home/user2/rep-sync1). impossible d'ecrire source = { "/home/user1/demo1/", "/home/user1/demo2/" } dans le fichier de config. Solution — Deux blocs vers la même target. modifié justes les lignes sources et target du 2eme bloc sync dans le fichier /etc/lsyncd/lsyncd.conf.lua 

# demo2 vers rep-sync2
sync {
    default.rsync,
    source  = "/home/user1/demo2/",
    target  = "root@192.168.100.226:/home/user2/rep-sync1",
    rsync   = {
        archive  = true,
        compress = true,
        verbose  = true,
        rsh      = "ssh -i /root/.ssh/id_sync -o StrictHostKeyChecking=no"
    }
}
⚠ Attention aux conflits :si /home/user1/demo1/ et /home/user1/demo2/ contiennent des fichiers avec le même nom, le dernier rsync à s'exécuter écrase le fichier — il n'y a pas de gestion de conflit.

lsyncd gère chaque bloc sync dans un processus parallèle. si un serveur est hors ligne, les autres continuent de se synchroniser normalement. simultané, en temps réel, indépendant 

Server1 
/home/user1/
    │
    ├──► 192.168.100.226 /home/user2/ - Server2
    ├──► 192.168.100.227 /home/user3/ - Server3
    ├──► 192.168.100.228 /home/user4/ - Server4
    └──► 192.168.100.229 /home/user5/ - Server5
⚠ NE PAS OUBLIER :La clé SSH doit être copiée sur chacune des 4 machines. On poura utiliser la methode precdente pour les differentes operations de copies. Tester la connexion de server1 vers Server{3,4,5}.
  • Performance limitée en Python pur — pas d'accélération GPU
  • Fonctionne uniquement sur des hashes non salés (MD5, SHA1)
  • Wordlists limitées en taille pour des raisons d'espace disque
  • Usage strictement réservé aux tests sur ses propres systèmes
