Sécurité des QR Codes

Vulnérabilité JWT Cryptographie Sécurité offensive

Les QR Codes sont omniprésents : paiements, contrôle d'accès, authentification. Encoder des données critiques en clair expose les systèmes à des attaques triviales de falsification. Ce projet démontre le vecteur d'attaque de bout en bout, et propose les contre-mesures cryptographiques appropriées.

Introduction

Un QR Code est simplement l'encodage visuel d'une chaîne de caractères. N'importe qui disposant d'un lecteur (de code qr appropriés, voire smartphone) peut lire, copier et modifier ce contenu. Lorsque des applications y stockent des données sensibles, montant d'un paiement, rôle utilisateur, identifiant de session, elles remettent de facto le contrôle à l'utilisateur final.

Ce projet explore trois axes : pourquoi c'est dangereux, comment l'attaque se déroule concrètement, et quelles protections cryptographiques mettre en place.

Le problème : données critiques en clair

Un QR Code n'est pas un coffre-fort

Contrairement à ce que son aspect visuel peut laisser croire, un QR Code n'offre aucune confidentialité et aucune intégrité par lui-même. Il encode une chaîne de caractères, souvent du JSON, XML ou tout autres format lisible par n'importe quel lecteur.

QR Code vulnérable

{
  "user_id": "1042",
  "nom":    "paul",
  "prenom":    "DUPON",
  "solde": 1500,
  "devise":  "XOF",
  "valide":  true
}

Toutes les données sont lisibles et modifiables. Ce QR Code ne contient aucune mesure de sécurité. Les données réelles doivent être stocker uniquement côté serveur.

⚠ Données à ne jamais encoder en clair dans un QR Code : montants financiers, rôles et permissions utilisateur, identifiants de session, codes de validation, droits d'accès, tokens de réinitialisation de mot de passe.

Vecteur d'attaque : falsification en 3 étapes

1
Scan et extraction L'attaquant scanne le QR Code avec n'importe quel lecteur (smartphone, ZBar, Python). Il obtient les informations en clair.
2
Modification des données critiques Il édite les informations : change "role":"user" en "role":"admin", ou "solde":1500 en "solde":2000000. Un simple éditeur de texte suffit.
3
Regénération du QR Code falsifié Il encode les nouvelles informations modifié dans un nouveau QR Code (qrcode.js, apps mobiles). Le résultat est visuellement identique à l'original.

Démo interactive

Les démonstrations ci-dessous reproduisent exactement ce qu'un attaquant peut réaliser avec de simples outils en ligne. Aucune compétence technique avancée n'est requise.

⚠ Cadre pédagogique : ces démonstrations sont réalisées dans un environnement isolé à des fins éducatives. Toute exploitation de cette technique sur des systèmes réels sans autorisation explicite est illégale.

Bonnes pratiques de sécurisation

Signature JWT — encoder une référence, pas les données

Le principe fondamental : le QR Code ne doit pas contenir les données critiques, mais une référence cryptographiquement signée permettant au serveur de retrouver et valider les données en base.

Header eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
Payload (ref. serveur uniquement) eyJ0eGlkIjoiVFhOLTQ0MiIsImV4cCI6MTc1MTMzNzYwMH0
.
Signature HMAC-SHA256 mK9xR2vTpLwQs8nZcF3hYdBvJeXoGiUA

Le payload ne contient que l'identifiant de transaction et une date d'expiration. Les données réelles (montant, rôle…) restent en base, accessibles uniquement après vérification cryptographique de la signature côté serveur. 

// Côté serveur — génération du QR sécurisé (Node.js)

// ✓ Ce qu'on encode dans le QR : uniquement une référence opaque
const payload = {
  txid: "TXN-20260607-0042",  // identifiant opaque, sans donnée critique
  iat:  1749734400,             // issued at
  exp:  1749734700             // expire dans 5 minutes
};

const token = jwt.sign(payload, process.env.JWT_SECRET, {
  algorithm: 'HS256'
});

// Contenu du QR Code → {"token": "eyJhbGci..."}
// Aucun montant, aucun rôle, aucune permission exposée.

// Côté serveur — vérification lors du scan
try {
  const decoded = jwt.verify(token, process.env.JWT_SECRET);
  const transaction = await db.getTransaction(decoded.txid);
  // ↑ Les vraies données viennent de la base, pas du QR Code
} catch(e) {
  // Token falsifié ou expiré → rejet immédiat
  res.status(401).json({ error: "QR Code invalide ou expiré" });
}
Pourquoi ça protège : si un attaquant modifie le token, la signature HMAC-SHA256 ne correspond plus. Le serveur rejette le QR Code falsifié instantanément, sans même chercher la transaction en base.

Durée de vie limitée — TTL court

Un QR Code sans expiration est exploitable indéfiniment après capture. Un TTL de 5 à 10 minutes réduit drastiquement la fenêtre d'exploitation. 

# Python — génération avec expiration courte
import jwt, datetime

payload = {
    "txid": "TXN-20260607-0042",
    "iat":  datetime.datetime.utcnow(),
    "exp":  datetime.datetime.utcnow() + datetime.timedelta(minutes=5)
}
token = jwt.encode(payload, os.getenv("JWT_SECRET"), algorithm="HS256")

# Vérification — exception levée automatiquement si expiré
try:
    decoded = jwt.decode(token, secret, algorithms=["HS256"])
except jwt.ExpiredSignatureError:
    return {"error": "QR Code expiré"}, 401
except jwt.InvalidTokenError:
    return {"error": "QR Code invalide"}, 401

Chiffrement JWE — confidentialité totale

JWT signe les données (intégrité) mais ne les chiffre pas (confidentialité). JWE (JSON Web Encryption) chiffre le payload : même le contenu du token devient illisible sans la clé privée du serveur. 

// JWE — chiffrement RSA-OAEP + AES-256-GCM (Node.js / jose)
const { CompactEncrypt } = require('jose');

const jwe = await new CompactEncrypt(
    new TextEncoder().encode(JSON.stringify(payload))
  )
  .setProtectedHeader({
    alg: 'RSA-OAEP-256',  // chiffrement de la clé symétrique
    enc: 'A256GCM'         // chiffrement du contenu (AES-256)
  })
  .encrypt(publicKey);

// Le QR Code contient un blob entièrement chiffré et illisible.
// Seul le serveur possédant la clé privée peut déchiffrer.

Récapitulatif des bonnes pratiques

🔏

Signature JWT

Signer chaque token avec HMAC-SHA256 ou RS256. Toute modification invalide la signature.

⏱

Expiration courte (TTL)

Limiter la validité à 5–10 minutes. Un QR capturé devient inutilisable rapidement.

🔐

Chiffrement JWE

Pour les cas très sensibles, chiffrer avec RSA-OAEP + AES-256-GCM. Contenu illisible.

🗄️

Données côté serveur

Ne jamais encoder montants, rôles ou permissions. Stocker uniquement un identifiant opaque.

🔂

Usage unique (nonce)

Invalider le token après sa première utilisation. Empêche la réutilisation d'un QR scanné.

🌐

Validation serveur

Vérifier la signature côté serveur, jamais côté client. Le client ne juge pas sa propre requête.

Règle d'or : un QR Code doit être traité comme une entrée utilisateur non fiable, au même titre qu'un paramètre HTTP. La confiance s'établit côté serveur, par vérification cryptographique — jamais par lecture directe du contenu.

Conclusion

Ce projet démontre qu'encoder des données critiques en clair dans un QR Code revient à laisser les clés du système entre les mains de l'utilisateur. L'attaque est triviale, ne nécessite aucun outil spécialisé, et peut avoir des conséquences graves : élévation de privilèges, fraude financière, contournement de contrôle d'accès.

La solution n'est pas de ne plus utiliser les QR Codes, mais de les utiliser correctement : comme un vecteur de transport d'une référence signée, et non comme un conteneur de données sensibles. L'architecture cible est claire : JWT signé + TTL court + données en base. Pour les cas les plus sensibles, JWE ajoute une couche de confidentialité.

Ces principes s'appliquent à tout système utilisant des QR Codes : paiements mobiles, contrôle d'accès physique, tickets d'événements, authentification 2FA.
